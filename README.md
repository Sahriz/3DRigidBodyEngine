# RigidBodyEngine

A rigid body physics engine being built from scratch in C++20. The current
application draws a triangle; the physics implementation is still planned.
Physics will run on the CPU, with OpenGL used to draw the result.

## Setup on Windows

Install these prerequisites:

1. Visual Studio 2022 or its Build Tools, with **Desktop development with C++**,
   the MSVC v143 toolset, and a Windows SDK. See Microsoft's
   [C++ installation guide](https://learn.microsoft.com/en-us/cpp/build/vscpp-step-0-installation?view=msvc-170).
2. [CMake](https://cmake.org/download/) 3.21 or newer, available on `PATH`, for
   the Visual Studio 2022 generator used below. The project itself declares
   CMake 3.20 as its minimum.
3. A graphics driver that supports **OpenGL 4.6**. The application requests a
   4.6 core context and the shaders use GLSL 460.

Both a C compiler and a C++20 compiler are needed: GLAD and GLFW compile as C.
The necessary dependency source files are included under `vendor/`, so GLFW,
GLAD, and GLM do not need separate installation or downloads during the build.

From the repository root, run these commands in PowerShell:

```powershell
cmake -S . -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Debug --parallel
.\build\bin\Debug\RigidBodyEngine.exe
```

Press Escape to close the window. For a release build, use `--config Release`
and run `.\build\bin\Release\RigidBodyEngine.exe`.

CMake embeds the absolute path to the source `shaders/` directory. Keep that
directory available when running the executable, and reconfigure/rebuild if
you move the checkout. This is currently a development layout rather than a
standalone executable distribution.

If `build/` was configured with another generator, use a different build
directory, such as `-B build/vs2022`, and adjust the build/run paths accordingly.
Visual Studio adds the configuration directory (`Debug` or `Release`) below
`bin/`; single-configuration generators such as Ninja do not.

## Vendored dependencies

The versions below describe the copies currently present in the repository.

| Library | Current copy | Files kept for this build |
| --- | --- | --- |
| [GLFW](https://www.glfw.org/) | Source snapshot declaring 3.5.0 | `CMakeLists.txt`, `CMake/`, `include/`, `src/`, `deps/wayland/`, license and attribution files |
| [GLAD](https://github.com/Dav1dde/glad/tree/v0.1.36) | Generated by GLAD 0.1.36 for OpenGL 4.6 | `src/glad.c`, `include/glad/glad.h`, `include/KHR/khrplatform.h` |
| [GLM](https://github.com/g-truc/glm) | Headers declaring 1.0.0 | Headers and inline implementations under `glm/`, plus `glm/copying.txt` |

`.gitignore` excludes GLFW's documentation, examples, tests, demo-only
dependencies, and alternate IDE/build files. It also excludes GLM's unused
standalone build and module sources. GLAD already contains only its three
required files. GLM's many `.hpp`, `.h`, and `.inl` files are its implementation
and remain included.

Keep GLFW's `CMake/` templates even though installation is disabled: its build
still reads them. Keep the Wayland protocol XML files for Linux builds, all
platform library sources, and the supplied license notices. The current CMake
configuration disables GLFW examples, tests, documentation, and installation.
To build GLFW's examples, tests, or documentation, restore the corresponding
upstream extras and change these settings in `CMakeLists.txt`.

If replacing a dependency manually, preserve these include locations:

```text
vendor/glad/include/glad/glad.h
vendor/glad/include/KHR/khrplatform.h
vendor/glad/src/glad.c
vendor/glfw/CMakeLists.txt
vendor/glfw/include/GLFW/glfw3.h
vendor/glfw/src/...
vendor/glfw/CMake/...
vendor/glfw/deps/wayland/...
vendor/glm/glm/glm.hpp
```

Use a compatible GLAD 1 loader when replacing GLAD; this code calls
`gladLoadGLLoader` and includes `<glad/glad.h>`. A GLAD 2 download requires code
and build changes. The current generated loader declares the compatibility
profile, while the application creates a core context; the core functions used
by this application are available in that loader.

## Other platforms

Windows with Visual Studio 2022 is the verified build path. Linux also needs
system OpenGL development files and GLFW's platform dependencies. The vendored
GLFW enables both X11 and Wayland by default, so install the relevant X11
development headers, Wayland development tools (including `wayland-scanner`),
`pkg-config`, and xkbcommon. See the
[GLFW compilation guide](https://www.glfw.org/docs/latest/compile.html) for
distribution-specific requirements. An X11-only build can use
`-DGLFW_BUILD_WAYLAND=OFF`.

The retained Cocoa backend does not make this application runnable on macOS
unchanged: its current OpenGL 4.6 context and GLSL 460 shaders require adaptation
for macOS's OpenGL support.

## Why CPU

Rigid body dynamics is a poor GPU fit at typical scales. Sequential impulses
(Gauss-Seidel) converge far faster than Jacobi and are inherently serial;
collision detection branches unpredictably with wildly varying work per pair;
and a normal scene is hundreds to low thousands of bodies, which is not
enough parallelism to amortise a kernel launch. The workload is
latency-bound, not throughput-bound. Box2D, Bullet and Jolt all work this way.

## Layout

    src/main.cpp   current window, shader and triangle setup
    src/core/      planned math types, transforms, timing utilities
    src/physics/   planned bodies, colliders, collision detection and solver
    src/render/    planned debug renderer, camera and shader loading
    shaders/        GLSL (found at runtime via the SHADER_DIR define)
    vendor/         glfw, glad, glm

## Local planning and assistant files

`PLAN.md` is a local roadmap and is intentionally ignored by Git. It is not
required to build the project and will not be present in a fresh clone.
Recognizable assistant instruction files, such as `AGENTS.md`, `CLAUDE.md`,
`GPT.md`, and `CODEX.md`, and assistant configuration/history directories are
also ignored. Source code and ordinary project documentation remain included.

Ignoring a file leaves the local copy on disk and excludes it from future Git
additions. It does not remove files that have already been committed.

## Resources

- **Box2D-lite** (github.com/erincatto/box2d-lite) - a complete 2D impulse
  engine in ~2000 lines by Erin Catto. Read this first, front to back. It is
  the single highest-value thing on this list.
- **Erin Catto's GDC slides** (box2d.org/publications) - "Modeling and
  Solving Constraints", "Soft Constraints", "Understanding Constraints".
  The sequential impulse method explained by its populariser.
- **Christer Ericson, _Real-Time Collision Detection_** - the reference for
  GJK, SAT, and every primitive intersection test. Buy it.
- **Dirk Gregorius' GDC talks** - "Robust Contact Creation", "Implementing
  QuickHull". The details nobody else writes down.
- **Jolt Physics** (github.com/jrouwe/JoltPhysics) - modern, readable,
  production-quality reference to compare your decisions against.
- **Glenn Fiedler, "Fix Your Timestep"** - planned for the bodies and motion
  milestone.

## Debugging note

There is no ground truth here. Bugs appear as slow drift over 30 seconds or
sudden explosive instability, both of which are miserable to bisect. Build
the debug renderer early - contact points, normals, impulse magnitudes,
AABBs - and treat it as part of the engine, not a nicety.
